# المرحلة 2: التحقق من المدخلات ومعالجة الأخطاء

اقرأ CLAUDE.md أولًا والتزم بقواعده، ثم نفّذ هذه المرحلة فقط. اقرأ الملفات المعنية فعليًا قبل التعديل، ميّز في تقريرك بين ما اختُبر وما استُنتج، واذكر عدد الاختبارات قبل/بعد (خط الأساس 365)، وقدّم الأوامر ونتائجها الفعلية.

## الخلفية
- `src/app/api/generate/route.ts` (حول الأسطر 616-628) يفعل `await req.json()` ويحوّله مباشرة إلى `GenerateRequest` بلا Zod ولا سقف حجم، بينما بقية المسارات تستخدم `readBoundedJson`.
- صور `frameImages` تُمرَّر base64 إلى المزود بلا فحص magic bytes أو حجم (المرجع الجيد: `src/agent/image-inspection.ts`).
- `console.log` يسجّل برومبت المستخدم كاملًا.
- `src/helpers/api-response.ts` (`executeApi`) يعيد 500 برسالة الخطأ الخام عند فشل `schema.parse`؛ ويستخدمه مسارا Lambda أيضًا.
- معالج `/api/plan` نفسه غير مغطى باختبار (الاختبارات تغطي `createDirectorPlan` فقط).

## المطلوب
- اختبارات تفشل أولًا: جسم كبير لـ `/api/generate`، جسم غير مطابق للمخطط، صورة بنوع/حجم غير صالح.
- أضف مخطط Zod لـ `GenerateRequest` وسقف بايتات عبر `readBoundedJson`، وأعد استخدام فحص الصور من `image-inspection.ts` (نوع فعلي، حجم، عدد).
- أزل تسجيل البرومبت الكامل؛ استبدله بتسجيل مُعمّى عبر `redaction.ts` (طول، معرّف طلب).
- أصلح `executeApi`: أخطاء التحقق ← 400 مع `issues` منظمة، أخطاء الخادم ← 500 برسالة عامة وتسجيل داخلي مُعمّى. حدّث مسارَي Lambda تبعًا لذلك.
- أضف اختبارات لمعالج `/api/plan` نفسه (استدعاء المسار لا الدالة الداخلية) وللمسارات المتأثرة.

## معيار القبول
- كل مسار API يتحقق ويحدّ حجم المدخل (جدول في `docs/api-validation.md`)، ولا رسائل خطأ خام تتسرب، ولا برومبت كامل في السجلات (اختبار يتحقق)، وعدد الاختبارات أعلى من 365.
