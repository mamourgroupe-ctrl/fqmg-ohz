## 2. Problems found in the supplied prototype (and the repo)

The prototype files (`src/agent/motion-rules.ts`, `frame-extractor.ts`, `vision-critique.ts`,
`loop.ts`, `tests/agent-loop.test.ts`) are **not present in this repository** (`src/agent/` did not
exist), so they could not be hardened or reproduced; everything here was written against the
repository. The prototype's reported Vitest mocking-order bug therefore could not be reproduced and
is not claimed to be fixed. The concrete problems that were found in *this* repository:

1. **No render-to-visual-review path existed at all** — no frame extraction, no visual critique, no
   budget/cost accounting, no authentication or rate limiting anywhere in `src/`.
2. **`/api/generate` had no motion-quality policy in its prompts**, so the model could emit
   specifications that violate the safe area, contrast, RTL, or minimum-size rules.
3. **A production build failure was introduced by the new job API**: importing the render backends
   pulls `@remotion/bundler` and `@remotion/renderer` into the server bundle, which resolve optional
   platform-native packages (`@remotion/compositor-*`, `@remotion/whisper-webgpu`,
   `@remotion/video-matting`) and esbuild's native binary. `next build` failed with 16 Turbopack
   errors until those packages were declared as runtime externals in `next.config.js`.
4. **A latent TDZ bug in the new job route**: the `run` callback read `job.jobId` while the job
   record was still being constructed (`Cannot access 'job' before initialization`), which made every
   job fail immediately. The identifier is now generated by the route and passed in.
5. **A task-id validation mismatch**: the job API composes task ids as `qa:<dedupe key>`, which the
   loop's job-id charset rejected, so every request failed validation. Task ids now have their own
   documented (wider) schema, since they are ledger labels and never paths.
6. **Fail-open credential checks**: `createModelForEntry` constructs a client without credentials, so
   an enabled repair provider looked configured even with no key; the runtime now requires
   `hasRequiredEnvVars(provider)`. Likewise the vision provider could not be enabled without an
   explicit "the model's documentation confirms image input" flag.
7. **Error text leaked internal paths** (`/home/user/...`): diagnostics now shorten any absolute path
   to its basename, on top of the existing secret redaction.

## 4. Architectural decisions

* **No second generation system and no second render pipeline.** The loop renders through the
  existing `src/remotion/entry.tsx` composition via the existing `RemotionAdapter`, and the existing
  `verifyRenderOutput` ffprobe gate runs before any critique. `/api/generate` keeps its behaviour and
  only gains the shared MOTION_RULES prompt section.
* **Background job + polling, not a long HTTP request.** `POST /api/agent/qa` returns `202` with a
  job id and poll path; the browser polls a validated view. This mirrors the existing Lambda
  progress hook rather than inventing a new mechanism.
* **Deterministic repair before paid repair.** Five rules have deterministic, data-only fixes; the AI
  repair provider is opt-in, used only when the local pass changed nothing, and its proposal is
  validated for identity/canvas/scene/asset integrity.
* **Explicit artifact contracts.** A local render is `local-file`; a Lambda render is `remote-url`.
  The browser never receives a filesystem path; local previews are streamed through an opaque route
  that re-validates the recorded path against allowed roots.
* **Safety over optimism.** Unknown pricing, an unverified vision capability, or a missing verdict
  all produce `needs_review`, never an approval.

## 5. Security controls

* `execFile` only (argument arrays, timeouts, output caps, no shell interpolation); only Remotion's
  bundled ffmpeg/ffprobe are executed.
* Path containment requires both a literal check and a `realpath` check, so symlinks inside an
  allowed root cannot escape it; downloads are written inside a pre-validated work directory.
* No generated code execution: the specification is data; repairs rewrite data only. A repair that
  changes project identity, canvas, fps, duration, scene ids/order, or assets is refused.
* Model output is untrusted: critique responses are Zod-validated and cross-checked ("approve" cannot
  carry a critical issue); malformed output becomes `critique-failed`.
* Images are validated by magic bytes and real dimensions before being sent, with MIME, byte, and
  count limits; the vision provider stays disabled without explicit enablement **and** an
  operator statement that the model's documentation supports images.
* Nothing internal leaves the server: job views are validated (with a redacted fallback), errors are
  redacted, and remote artifacts are never proxied.
* Bounded work: ≤ 4 iterations (default 2), ≤ 8 frames (default 4), 128 KB request cap, 32 active
  jobs, job TTL cleanup that deletes retained previews.

## 6. Budget controls

| Control | Value |
| --- | --- |
| Task ceiling | 0.03 USD (`AGENT_TASK_BUDGET_USD`) |
| Daily ceiling | 0.25 USD UTC (`AGENT_DAILY_BUDGET_USD`) |
| Pricing | Operator-supplied, source-stamped only; unknown price ⇒ the paid call is refused |
| Reservation | reserve → settle (request may have been dispatched) or release (it provably was not) |
| Exception | `user-approved-exception` with `approvedBy`/`maxUsd`/`reason`; cannot raise the daily ceiling |
| Honesty | Every view reports `enforcement: "process-local"` and `invoiceGuarantee: false`; the app-side counter does not bound the provider's invoice and nothing silently falls back to another paid provider |

## 9. Remaining limitations

* Single-instance, in-process job registry and budget ledger: lost on restart, not shared between
  instances; there is still no authentication or distributed rate limiting in front of the routes.
* The local render path is wired and unit-tested but has never completed a real render in this
  environment (no browser, §7). The Lambda path has never run (no AWS credentials).
* Visual critique requires an operator-verified vision model and a verified price; until both are
  configured, the loop reports `needs_review`.
* The bundled ffmpeg is a stripped build: the extractor records the requested timestamp, the fact
  that a frame exists there, and the SHA-256 of the reviewed bytes — not pixel-exact frame identity.
* Audio, subtitles, and custom fonts are still refused by the renderer adapter.
* A long or variable-frame-rate video can exhaust the bounded frame-timeline probe; that path fails
  closed rather than guessing.
